## 2) المتبقي (بالأولوية)

### أ) مصدر ثالث للموقع في `MainActivity` (عالية)
`startFusedLocationUpdates` يعمل **موازياً** لمسار `MainViewModel` المفلتر ويكتب `viewModel.updateUserLocation(...)` مباشرة، فيعود الخلل الذي أصلحناه في المستند 39:
- يقبل `lastLocation` و`LocationManager.getLastKnownLocation(GPS/NETWORK)` **بلا فحص العمر** (قد يكون عمرهما أياماً) وبلا فحص الدقة ولا تجاهل مواقع المحاكاة.
- لا يمرّ عبر `markFix()` فيختلط مع الفلاتر؛ وأثناء الملاحة يكتب كل 2–4 ث قراءات غير مفلترة بجانب تدفق الملاحة (تذبذب وانحراف كاذب).
- يعمل بدقة عالية **طوال عمر النشاط** (استنزاف بطارية) حتى خارج الخريطة.
**الحل: مسار واحد يملكه `MainViewModel`، ويتحكم النشاط بدورة الحياة فقط.**
في `MainActivity`:
```kotlin
// 1) احذف: الدالة startFusedLocationUpdates كاملة، والحقل locationCallback، وكتلة إلغائه في onDestroy.
// 2) أضف:
```

ولتوحيد المالك احذف من `MapScreenContent` سطر `DisposableEffect(Unit) { onDispose { viewModel.stopLocationUpdates() } }` الذي أضفناه في المستند 26/31 (النشاط صار صاحب الإيقاف).

**اختبار:** بدّل الخريطة/الخروج للشاشة الرئيسية: يختفي مؤشر GPS في شريط الحالة خلال ثوانٍ، ولا قفزات للموقع أثناء الملاحة.

### ب) App Check والتوزيع من GitHub (عالية، تحقق منها الآن)
المزوّد في الإصدار هو **Play Integrity**. التطبيقات المثبّتة من ملف APK خارج Google Play (كنسخ GitHub) **تفشل عادةً** في هذا الفحص. إن كان «Enforce» مفعّلاً في Firebase لـ Firestore/Storage/Auth فستفشل كل طلبات النسخة الموزّعة خارج المتجر (لا بيانات ولا فزعة). قبل التوزيع:
1. افتح Firebase Console ← App Check، وتحقق هل التطبيق في وضع Enforce.
2. إن كنت ستوزّع APK من GitHub فاترك الـ Enforce معطّلاً (وضع المراقبة فقط)، أو اعتمد مزوّداً مخصصاً؛ ولا تفعّل الإنفاذ إلا لنسخ المتجر.
3. اختبر نسخة موقّعة مثبّتة يدوياً قبل النشر.

### ج) `NetworkUtils.isNetworkAvailable` صارمة أكثر من اللازم (متوسطة)
تشترط `NET_CAPABILITY_VALIDATED`. هذه العلامة لا تُضبط إن كان فحص الاتصال الخاص بأندرويد محجوباً أو بطيئاً عند المزوّد، فتظهر الشبكة «بلا إنترنت» رغم أنها تعمل (شائع مع بعض مزودي الخدمة). النتيجة: يُعتبر التطبيق «أوفلاين» خطأً وتتأخر المزامنة.
```kotlin
object NetworkUtils {
    /** وجود شبكة قد تحمل إنترنت (بلا اشتراط التحقق). استخدمها للقرار؛ وأي فشل فعلي يُعالَج عند الطلب. */
    fun hasInternetTransport(context: Context): Boolean = try {
        val cm = context.getSystemService(Context.CONNECTIVITY_SERVICE) as? ConnectivityManager
        val caps = cm?.activeNetwork?.let { cm.getNetworkCapabilities(it) }
        caps?.hasCapability(NetworkCapabilities.NET_CAPABILITY_INTERNET) == true
    } catch (e: Exception) { false }

    /** شبكة مُتحقَّق منها (للعرض فقط: «متصل ومستقر»). */
    fun isValidatedNetwork(context: Context): Boolean = try {
        val cm = context.getSystemService(Context.CONNECTIVITY_SERVICE) as? ConnectivityManager
        val caps = cm?.activeNetwork?.let { cm.getNetworkCapabilities(it) }
        caps?.hasCapability(NetworkCapabilities.NET_CAPABILITY_INTERNET) == true &&
            caps.hasCapability(NetworkCapabilities.NET_CAPABILITY_VALIDATED)
    } catch (e: Exception) { false }

    fun isNetworkAvailable(context: Context) = hasInternetTransport(context)     // للتوافق مع المستدعين الحاليين
}
```
وفي `OfflineQueueManager.isOnline()` استعمل `hasInternetTransport` (وليس VALIDATED)، فالمحاولة الفعلية مع `backoff` هي الحكم.

### د) Analytics بلا موافقة (متوسطة)

### و) `DeepSystemDiagnosticOrchestrator` (متوسطة)
- `durationMs = 350L` **ثابت** لكل خطوة (زمن مختلق في التقارير)، وتسمية «يعمل 100%» و«نجاح التحقق بنسبة 100%». اجعل الزمن مقيساً: `val t0 = android.os.SystemClock.elapsedRealtime()` حول جسم كل خطوة و`durationMs = SystemClock.elapsedRealtime() - t0`، واحذف عبارات «100%».
- `passed` يأتي من المستدعي؛ تأكد أن كل خطوة تقرأ نتيجة حقيقية (قراءة من Firestore/تحقق) وليس `true` مباشرة.

- `NavConfig`: قائمة `YEMEN_CITIES` ما زالت مكررة مع `OfflineMapManager` و`CityAliases`؛ وحّد المصدر عند أول فرصة (لا خطر وظيفي الآن).
